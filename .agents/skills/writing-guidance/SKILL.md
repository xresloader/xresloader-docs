# 写作规范

交付读者能理解和使用的文字，保留事实、技术含义和作者判断。遵循目标文本的语言、读者与已有文风；中文说明、英文注释和双语文本分别按其语境处理。

## 输入与范围

先从请求和材料确定目标文本、用途、读者、语言及不可改动的内容。改写先完整读取原稿与直接相关的代码、引用和图表；新写先整理已有材料。能从上下文确定的事项直接采用，影响结论的缺口才澄清。

本站工具参数、版本和示例事实按 [docs-maintenance](../docs-maintenance/SKILL.md) 核验；页面、CSS 或构建行为按 [site-change](../site-change/SKILL.md) 处理。本 Skill 负责文字，不替代这些检查，也不要求单句修改执行长文流程。

## 日常流程

1. 标记必须保留的事实、术语、立场、引文和格式。区分已验证、推断与未知；材料不足时先写有依据的部分或列待补问题，不编造数字、来源、经历和检查结果。
2. 先修事实与论证，再调整结构，最后处理语法与措辞。决策说明可先给判断；教程交代前提、步骤和结果；推导、复盘与文章保留有助理解的过程，不强凑三点或等长章节。
3. 写清对象、动作、条件和结果，用准确动词减少空泛名词。删除不推进内容的开场、转场、夸大评价和重复小结；列表用于步骤或并列项，表格用于比较，连续解释用自然段。
4. 保留有依据的第一人称、怀疑、取舍、批评与适度口语。没有作者样本时采用清楚克制的表达，不虚构个人故事、注入口头禅或宣称已恢复作者风格。
5. 按上下文检查措辞与句式，不执行禁词表或全局替换。删去无用的否定对比，保留真实纠正、区分和排除；简化递进句时保留前后两项事实。术语保持一致。
6. 对照修改前后复核否定、条件、数量、单位、时序、因果、承诺强度及验证状态。保留标识符、配置键、命令、路径、协议文字、原始输出和必要格式；发现功能问题时单独处理。
7. 通读相关段落及全文中的重复模式，只改有问题的部分。后续润色没有可说明的改善或开始损失语义、作者特点时停止或撤回该轮修改；不靠错字、随机句长或检测器分数制造自然感。

## 按需细节

- 处理长文结构、对举/转折/递进、易混术语、技术语义或站点格式时，读 [详细规则](references/writing-rules.md) 的相关章节。
- 判断改写是否遗漏事实、抹平作者判断或误伤正常表达时，读 [改写与保留示例](references/examples.md)。示例是假设材料，不能当成本站功能或验证结果。
- 更新规则本身时，核对 [来源索引](../../../docs/ai/source-index.md) 的写作规范记录与失败样例，按 [触发与质量评估](../../../docs/ai/skill-evaluation.md) 比较同材料的新写或同原稿的润色；未运行的对照保留未测状态。

## 验证与交付

确认读者能复述要点、找到条件并采取所需行动；叙事或评论检查是否保留核心观察与判断。对照原文核查语义和作者声音，检查链接、frontmatter、代码围栏、锚点及资源。按 [工程工作流](../../../docs/ai/engineering-workflow.md) 选择验证：公开页面涉及 MDX、链接或资源时构建；内部规则检查 Markdown、引用与 Skill 格式，结束前执行 `git diff --check`。

报告改了什么、依据和实际检查，区分尚未验证、缺少真实样本与验证未通过。构建通过不能证明代码示例或上游行为正确。交付正文保留必要披露，去掉助手寒暄、编辑批注和占位文字；不把检查清单机械附在每篇成稿后。
